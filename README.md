# suppliers-parser

Парсер поставщиков Yopt и ProductCenter с сохранением в SQLite и экспортом в Excel.

Перед первым запуском примените миграции: `make migrate-up`.

```bash
# Обход сайта: добавить новые компании, пропустить уже сохранённые.
go run ./cmd/parse --sources productcenter

# Обход сайта: обновить существующие компании и прайсы, добавить новые.
go run ./cmd/parse --sources productcenter --force

# Только дозагрузка отсутствующих или пустых файлов по ссылкам из БД.
go run ./cmd/parse --sources all --downloads-only
```

`--force` сразу начинает парсинг сайта и не выполняет предварительную дозагрузку старых ссылок. `--downloads-only` не обходит страницы компаний; эти два флага несовместимы. Существующий скачанный файл сохраняется, если его повторная загрузка завершилась ошибкой.

Временные файлы `.download-*` удаляются после успеха, ошибки или штатной отмены через `Ctrl+C`. При запуске удаляются также остатки `.download-*` и пустые файлы старого загрузчика `yopt_<id>_*` / `productcenter_<id>_*`, не изменявшиеся более 10 минут. Свежие файлы оставляются для защиты текущих загрузок; обычные непустые файлы не удаляются.

## Подбор конечных категорий

Отдельная программа работает локально, без API-ключей и платных запросов:

```bash
go run ./cmd/categorize --input companies.xlsx --categories category-normal --limit 5
```

По умолчанию берёт **первые пять компаний в порядке листа «Компании»**, включая компании без товаров. Связывает товары из листа «Товары» по названию компании и ИНН. При неоднозначной связи выдаёт предупреждение и не смешивает товары разных компаний.

Результаты: `outputs/category-preview/report.md` для просмотра и `report.json` для дальнейшей обработки. Категории сопровождаются товарами-основаниями и номерами строк Excel. `--out` меняет каталог отчётов; `--limit` — размер выборки. Excel и БД не изменяются.

Это предварительный классификатор на правилах: нормализация словоформ, названия конечных категорий и явные синонимы из `config/category-aliases.json`. Это **не LLM и не универсальный семантический поиск**. Незнакомые формулировки остаются без решения. Описания сохраняются в JSON для проверки, но не участвуют в автоматическом подборе: в них часто упоминаются принадлежности, поверхности и сторонние товары. Содержимое файлов прайс-листов пока не читается.

Словарь можно расширить правилом:

```json
{
  "category": "Ноутбуки",
  "phrases": ["ноутбук", "ультрабук", "персональный мобильный компьютер"],
  "exclude": ["сумка", "чехол", "подставка"]
}
```

Добавьте объект в массив `aliases`. `category` должна точно соответствовать названию в справочнике. Фразы проверяются в названии товара с простой нормализацией словоформ. Для категории с явными правилами автоматическое совпадение по её названию отключается; перечислите нужные варианты в `phrases`. `--aliases` позволяет указать другой словарь; `--aliases=''` оставляет только совпадения по названиям категорий.

Одинаковые названия справочника объединяются. ID категории — номер её первого вхождения, поэтому он изменится при перестановке строк; для постоянного хранения позже нужен справочник со стабильными ID и полными путями. Источник данных реализует `categorize.CompanySource`: адаптер SQLite сможет заменить `ExcelSource`, не меняя классификатор.

### Полный словарь и проверка на всех компаниях

`category-aliases.json` содержит одну запись на каждое уникальное название `category-normal`. Поле `kind` различает:

- `literal`: только название категории; расширенные смысловые синонимы ещё не описаны.
- `synonyms`: явные синонимы, сокращения или обязательные контекстные формулировки.
- `taxonomy_examples`: виды товаров из скобок самого справочника.
- `context_required`: название не определяет товар без родительского пути; `enabled: false` отключает автоматическое назначение, а `note` объясняет причину.

Наличие записи для каждой категории не означает полный охват всех формулировок. Для неоднозначных названий нельзя автоматически восстанавливать родительские разделы. При добавлении категорий обновите словарь: тест `TestFullDictionaryCoverage` проверяет соответствие один к одному.

Сопоставление учитывает перестановку слов и до двух вставленных слов в многословной фразе. Проверки предмета продажи блокируют совпадения с назначением, материалом, отсутствующими частями и принадлежностями. Есть отдельные исключения для категорий. Правила предварительно индексируются по словам, поэтому большой справочник не перебирается заново для каждого товара.

Полный прогон текущего Excel (518 компаний):

```bash
go run ./cmd/categorize --limit 518 --out outputs/category-full
go test ./internal/categorize
```

В начале отчёта приведено покрытие: число компаний с товарами, компаний с категориями и распознанных товарных строк. Это не измерение точности: для него нужна независимая ручная разметка. `internal/categorize/testdata/regression.json` содержит положительные и отрицательные примеры для контроля известных ошибок.

## Поиск руководителей по ИНН/ОГРН

Отдельная команда обогащает уже сохранённые компании из обоих адаптеров через [DaData «Организация по ИНН»](https://dadata.ru/api/find-party/). Обход сайтов для этого не нужен. Требуется API-ключ DaData в переменной окружения `DADATA_API_KEY`; ключ не передаётся в аргументах команды и не сохраняется в отчёте или БД. `.env` автоматически не загружается.

```bash
# Применить новую миграцию 000004.
make migrate-up

# Проверить первые 5 компаний без API-ключа, запросов и изменений БД.
go run ./cmd/enrich --dry-run --limit 5 --out outputs/leadership/preview.json

# Задать ключ в текущем терминале, не записывая его в историю команд.
read -rsp 'DaData API key: ' DADATA_API_KEY
export DADATA_API_KEY

# Обработать первые 5 активных компаний.
go run ./cmd/enrich --limit 5

# Обработать компании обоих источников; свежие результаты берутся из кеша.
go run ./cmd/enrich --sources all

# Принудительно обновить сведения только для ProductCenter.
go run ./cmd/enrich --sources productcenter --force
```

Флаги: `--db` (по умолчанию `data.db`), `--sources` (`all`, `yopt`, `productcenter` или список через запятую), `--limit` (0 — все), `--ttl` (720h), `--retry-after` (1h), `--delay` (1s), `--timeout` (20s), `--out` (по умолчанию `outputs/leadership/report.json`). Параметры длительности используют синтаксис Go: `30m`, `24h`, `720h`.

### Поведение и сохранение

- Проверяются контрольные цифры ИНН. Если он отсутствует или неверен, используется корректный ОГРН/ОГРНИП. По названию компании поиск не выполняется.
- Запрашивается головная организация. Если нужны руководители филиалов, потребуется отдельное сопоставление по КПП; текущая команда их не определяет.
- ИНН/ОГРН ответа сверяются с известными корректными реквизитами компании. Противоречия получают `needs_review`, без назначения руководителя.
- `leadership_cache` хранит результат по поисковому реквизиту и последнюю попытку. Одинаковый ИНН у двух адаптеров запрашивается один раз за запуск, включая `--force`; успешные ответы, в том числе отрицательные, кешируются на 30 дней. Поиск по ОГРН использует отдельный ключ кеша.
- `company_leadership` хранит связь с компанией, статус, время попытки и JSON результата. Стандартный парсинг не перезаписывает эти сведения. В JSON есть источник, дата проверки, дата актуальности данных реестра (если предоставлена), тип лица и список руководителей.
- Типы руководителей: `PERSON` — физлицо, `LEGAL` — управляющая организация, `INDIVIDUAL` — сам ИП. `UNKNOWN` означает, что базовый ответ не позволяет установить тип; результат требует проверки. Полный массив руководителей обрабатывается, если он предоставлен тарифом DaData. Учредители не используются вместо руководителей.
- Статусы: `found`, `no_management`, `not_found`, `needs_review`, `invalid_identifier`, `error`. В `--dry-run` корректные реквизиты получают `pending`.
- Ошибки API не стирают прежний результат. Поэтому при `status=error` поле `result` может содержать **старые** сведения с прежним `checked_at`. При следующем запуске повтор возможен после `--retry-after`; `--force` обходит эту паузу. Внутри одного запуска автоматических повторов нет.
- HTTP 401/403/429 останавливают обработку, сохраняется частичный отчёт с причиной и числом обработанных компаний. После устранения причины команду можно запустить снова. Сетевые и серверные ошибки остальных компаний сохраняются, обработка продолжается.

Сравнение названий служит человеку для проверки: юридическое имя из DaData сохраняется в результате рядом с исходным названием. Совпадение по реквизитам является основным критерием. Наличие записи в реестре не означает, что руководитель указан на сайте поставщика или что источник обновился сегодня.
