# suppliers-parser

Парсер поставщиков Yopt и ProductCenter с сохранением в SQLite и экспортом в Excel.

**[Справочник команд и флагов](docs/CLI.md)** — значения по умолчанию, несовместимые сочетания, режимы работы и готовые сценарии для всех пяти команд.

Перед первым запуском примените миграции: `make migrate-up`.

```bash
# Обход сайта: добавить новые компании, обогатить новые и встреченные существующие.
go run ./cmd/parse --sources productcenter

# Обход сайта: обновить существующие компании и прайсы, добавить новые.
go run ./cmd/parse --sources productcenter --force

# Только дозагрузка отсутствующих или пустых файлов по ссылкам из БД.
go run ./cmd/parse --sources all --downloads-only
```

`--force` сразу начинает парсинг сайта и не выполняет предварительную дозагрузку старых ссылок. `--downloads-only` не обходит страницы компаний; эти два флага несовместимы. Существующий скачанный файл сохраняется, если его повторная загрузка завершилась ошибкой.

Временные файлы `.download-*` удаляются после успеха, ошибки или штатной отмены через `Ctrl+C`. При запуске удаляются также остатки `.download-*` и пустые файлы старого загрузчика `yopt_<id>_*` / `productcenter_<id>_*`, не изменявшиеся более 10 минут. Свежие файлы оставляются для защиты текущих загрузок; обычные непустые файлы не удаляются.

## Подбор конечных категорий

Отдельная программа работает локально, без API-ключей и платных запросов:

```bash
go run ./cmd/categorize --input companies.xlsx --categories category-normal --limit 5
```

По умолчанию берёт **первые пять компаний в порядке листа «Компании»**, включая компании без товаров. Связывает товары из листа «Товары» по названию компании и ИНН. При неоднозначной связи выдаёт предупреждение и не смешивает товары разных компаний.

Результаты: `outputs/category-preview/report.md` для просмотра и `report.json` для дальнейшей обработки. Категории сопровождаются товарами-основаниями и номерами строк Excel. `--out` меняет каталог отчётов; `--limit` — размер выборки. В режиме `--input` Excel и БД не изменяются; режим `--db` сохраняет категории в SQLite.

Это предварительный классификатор на правилах: нормализация словоформ, названия конечных категорий и явные синонимы из `config/category-aliases.json`. Это **не LLM и не универсальный семантический поиск**. Незнакомые формулировки остаются без решения. Описания сохраняются в JSON для проверки, но не участвуют в автоматическом подборе: в них часто упоминаются принадлежности, поверхности и сторонние товары. В режиме Excel файлы прайс-листов не читаются; в режиме SQLite поддерживаются скачанные XLSX/XLS/CSV и текстовые PDF.

Словарь можно расширить правилом:

```json
{
  "category": "Ноутбуки",
  "phrases": ["ноутбук", "ультрабук", "персональный мобильный компьютер"],
  "exclude": ["сумка", "чехол", "подставка"]
}
```

Добавьте объект в массив `aliases`. `category` должна точно соответствовать названию в справочнике. Фразы проверяются в названии товара с простой нормализацией словоформ. Для категории с явными правилами автоматическое совпадение по её названию отключается; перечислите нужные варианты в `phrases`. `--aliases` позволяет указать другой словарь; `--aliases=''` оставляет только совпадения по названиям категорий.

Одинаковые названия справочника объединяются. ID категории — номер её первого вхождения, поэтому он изменится при перестановке строк; для постоянного хранения позже нужен справочник со стабильными ID и полными путями. Excel и SQLite используют один классификатор; SQLite связывает товарные строки по ID компании и сохраняет названия нормальных категорий.

### Полный словарь и проверка на всех компаниях

`category-aliases.json` содержит одну запись на каждое уникальное название `category-normal`. Поле `kind` различает:

- `literal`: только название категории; расширенные смысловые синонимы ещё не описаны.
- `synonyms`: явные синонимы, сокращения или обязательные контекстные формулировки.
- `taxonomy_examples`: виды товаров из скобок самого справочника.
- `context_required`: название не определяет товар без родительского пути; `enabled: false` отключает автоматическое назначение, а `note` объясняет причину.

Наличие записи для каждой категории не означает полный охват всех формулировок. Для неоднозначных названий нельзя автоматически восстанавливать родительские разделы. При добавлении категорий обновите словарь: тест `TestFullDictionaryCoverage` проверяет соответствие один к одному.

Сопоставление учитывает перестановку слов и до двух вставленных слов в многословной фразе. Проверки предмета продажи блокируют совпадения с назначением, материалом, отсутствующими частями и принадлежностями. Есть отдельные исключения для категорий. Правила предварительно индексируются по словам, поэтому большой справочник не перебирается заново для каждого товара.

Полный прогон текущего Excel (518 компаний):

```bash
go run ./cmd/categorize --limit 518 --out outputs/category-full
go test ./internal/categorize
```

В начале отчёта приведено покрытие: число компаний с товарами, компаний с категориями и распознанных товарных строк. Это не измерение точности: для него нужна независимая ручная разметка. `internal/categorize/testdata/regression.json` содержит положительные и отрицательные примеры для контроля известных ошибок.

## Поиск руководителей по ИНН/ОГРН

Отдельная команда обогащает уже сохранённые компании из обоих адаптеров через [DaData «Организация по ИНН»](https://dadata.ru/api/find-party/). Обход сайтов для этого не нужен. Требуется API-ключ DaData в переменной окружения `DADATA_API_KEY`; ключ не передаётся в аргументах команды и не сохраняется в отчёте или БД. `.env` автоматически не загружается.

```bash
# Применить новую миграцию 000004.
make migrate-up

# Проверить первые 5 компаний без API-ключа, запросов и изменений БД.
go run ./cmd/enrich --dry-run --limit 5 --out outputs/leadership/preview.json

# Задать ключ в текущем терминале, не записывая его в историю команд.
read -rsp 'DaData API key: ' DADATA_API_KEY
export DADATA_API_KEY

# Обработать первые 5 активных компаний.
go run ./cmd/enrich --limit 5

# Обработать компании обоих источников; свежие результаты берутся из кеша.
go run ./cmd/enrich --sources all

# Принудительно обновить сведения только для ProductCenter.
go run ./cmd/enrich --sources productcenter --force
```

Флаги: `--db` (по умолчанию `data.db`), `--sources` (`all`, `yopt`, `productcenter` или список через запятую), `--limit` (0 — все), `--ttl` (720h), `--retry-after` (1h), `--delay` (1s), `--timeout` (20s), `--out` (по умолчанию `outputs/leadership/report.json`). Параметры длительности используют синтаксис Go: `30m`, `24h`, `720h`.

### Поведение и сохранение

- Проверяются контрольные цифры ИНН. Если он отсутствует или неверен, используется корректный ОГРН/ОГРНИП. По названию компании поиск не выполняется.
- Запрашивается головная организация. Если нужны руководители филиалов, потребуется отдельное сопоставление по КПП; текущая команда их не определяет.
- ИНН/ОГРН ответа сверяются с известными корректными реквизитами компании. Противоречия получают `needs_review`, без назначения руководителя.
- `leadership_cache` хранит результат по поисковому реквизиту и последнюю попытку. Одинаковый ИНН у двух адаптеров запрашивается один раз за запуск, включая `--force`; успешные ответы, в том числе отрицательные, кешируются на 30 дней. Поиск по ОГРН использует отдельный ключ кеша.
- `company_leadership` хранит связь с компанией, статус, время попытки и JSON результата. Парсер обновляет эти сведения через общий механизм обогащения с кешем. В JSON есть источник, дата проверки, дата актуальности данных реестра (если предоставлена), тип лица и список руководителей.
- Типы руководителей: `PERSON` — физлицо, `LEGAL` — управляющая организация, `INDIVIDUAL` — сам ИП. `UNKNOWN` означает, что базовый ответ не позволяет установить тип; результат требует проверки. Полный массив руководителей обрабатывается, если он предоставлен тарифом DaData. Учредители не используются вместо руководителей.
- Статусы: `found`, `no_management`, `not_found`, `needs_review`, `invalid_identifier`, `error`. В `--dry-run` корректные реквизиты получают `pending`.
- Ошибки API не стирают прежний результат. Поэтому при `status=error` поле `result` может содержать **старые** сведения с прежним `checked_at`. При следующем запуске повтор возможен после `--retry-after`; `--force` обходит эту паузу. Внутри одного запуска автоматических повторов нет.
- HTTP 401/403/429 останавливают обработку, сохраняется частичный отчёт с причиной и числом обработанных компаний. После устранения причины команду можно запустить снова. Сетевые и серверные ошибки остальных компаний сохраняются, обработка продолжается.

Сравнение названий служит человеку для проверки: юридическое имя из DaData сохраняется в результате рядом с исходным названием. Совпадение по реквизитам является основным критерием. Наличие записи в реестре не означает, что руководитель указан на сайте поставщика или что источник обновился сегодня.

## Автоматическая обработка и SQLite

`go run ./cmd/parse --sources all` после сохранения каждой компании и её товарных строк назначает нормальные категории и запрашивает руководителя. Первый проход выполняется до загрузки файлов; после загрузки категории пересчитываются с учётом файловых прайсов. Уже существующие компании, встреченные при обходе, также обрабатываются без `--force`. `--downloads-only` дозагружает файлы и пересчитывает категории затронутых компаний, без обхода сайтов и запросов DaData.

Ключ `DADATA_API_KEY` нужен для поиска руководителя. Если ключ отсутствует, в журнале появляется предупреждение, а парсинг и категоризация продолжаются. Запросы обоих адаптеров сериализованы, между запросами выдерживается секунда; используется кеш 30 дней. `--force` обновляет данные сайта, но не сбрасывает кеш DaData (для этого есть `cmd/enrich --force`). При 401/403/429 поиск останавливается до следующего запуска, остальные этапы продолжаются.

Перед миграцией 000005 сделайте резервную копию SQLite через SQLite backup API. Миграция добавляет `company.category_normal_json`: JSON-массив названий, например `["Ноутбуки", "Мониторы"]`. Категории назначаются по активным товарным строкам, связанным по ID компании. Нет подтверждённых совпадений — `[]`; скачанные файлы автоматически разбираются при категоризации.

Чтобы обработать всю существующую БД без обхода сайтов:

```bash
go run ./cmd/categorize --db data.db --limit 0 --out outputs/category-sqlite
go run ./cmd/enrich --sources all
go run ./cmd/geography --db data.db
go run ./cmd/export --db data.db --out companies.xlsx
```

`cmd/categorize --input companies.xlsx` сохраняет прежний режим отчёта из Excel. `--categories` и `--aliases` доступны также парсеру.

Экспорт включает нормальные категории, руководителя и его должность. Отсутствующие сведения остаются пустыми; управляющая организация выводится своим названием. Несколько руководителей и должностей занимают соответствующие строки внутри ячеек. ID, даты, активность, Telegram и ВК исключены из Excel; служебные поля остаются в БД. Журналы всех команд используют единый формат `дата время [компонент] сообщение`.

## Товары из файловых прайсов

Перед запуском примените миграцию 000006 (`make migrate-up`) к резервной копии или после бэкапа БД. Таблица `price_file_extraction` хранит результаты извлечения, SHA-256 содержимого и версию парсера. Неизменённые файлы повторно не разбираются; ошибки запуска инструментов не кешируются и могут быть повторены после установки зависимостей.

Поддерживаются XLSX/XLSM (через excelize), XLS (через установленный `libreoffice`), CSV/TSV (UTF-8 и Windows-1251, разделители запятая/точка с запятой/табуляция), PDF с текстовым слоем (через `pdftotext`, пакет `poppler-utils`). На Debian/Ubuntu зависимости устанавливаются командой `sudo apt install libreoffice-calc poppler-utils`. LibreOffice запускается с отдельным временным профилем, который удаляется после обработки.

Извлечение ищет явный заголовок наименования товара, обрабатывает несколько листов и повторные шапки, исключает итоги и отдельные заголовки разделов. PDF читаются с сохранением расположения колонок. Сканированные PDF не распознаются: статус `no_text`. Необычная таблица без распознанной шапки получает `no_table`; документы и презентации не классифицируются целиком как товар. Сложная вёрстка, повреждённый текстовый слой и нестандартные заголовки могут потребовать ручной проверки.

Лимиты: файл до 64 MiB, лист/CSV до 100 000 строк, внешняя обработка до 60 секунд. Ошибки отдельных файлов попадают в журнал и предупреждения отчёта; inline-товары продолжают обрабатываться. Товары объединяются по названию без учёта регистра и лишних пробелов. Отчёты JSON/Markdown сохраняют файл, лист, строку и страницу для проверки основания категории.

Для обработки уже скачанных файлов без повторного обхода сайтов:

```bash
go run ./cmd/categorize --db data.db --limit 0 --out outputs/category-files
go run ./cmd/geography --db data.db
go run ./cmd/export --db data.db --out companies.xlsx
```

Лист «Товары» Excel-экспорта пока содержит исходные inline-товары; извлечённые файловые товары доступны в отчёте категоризации и `price_file_extraction.products_json`. Нормальные категории в экспорте учитывают оба источника.

## Пагинация товаров Yopt

Адаптер Yopt обходит все страницы списка товаров по ссылке «следующая», объединяет ссылки без дублей и затем читает карточки товаров. При ошибке загрузки страницы или карточки новый неполный inline-прайс не сохраняется; ранее сохранённые товары остаются в БД. Циклические ссылки пагинации считаются ошибкой. Дополнительных флагов для пагинации нет.

## Российские компании

После миграции 000007 выполните `go run ./cmd/geography --db data.db` (или `./bin/geography --db data.db` после `make build`). Это отдельный локальный механизм: он определяет страну по сохранённым сведениям DaData, реквизитам и явной стране в адресе. Запросов к сайтам и DaData нет. `is_russian` хранит `1` (российская), `0` (иностранная), `NULL` (не определено/противоречие). Причины решений сохраняются в `outputs/geography/report.json` рядом с БД. Проверка пары реквизитов является эвристикой, не проверкой реестра.

Экспорт на всех листах включает **только `is_russian = 1`**. Данные остальных компаний остаются в БД. Запускайте `geography` после парсинга/обновления руководителей и перед экспортом; новые компании пока не классифицированы. При изменении ИНН, ОГРН или адреса парсер сбрасывает старую классификацию. Все активные компании обоих источников пересчитываются при каждом запуске механизма.
